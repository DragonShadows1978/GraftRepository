# Alias design options — for David

**Reasoning recommendation: investigate (b) fold-merge first; retain (a) two-hop read as the fallback for an unfused edge. Implement none of these in r3.** Existing receipts favour a compact combined record, but do not establish that the current librarian selects the right alias/base pair or that a resulting digest answers the Signal probes. Alias resolution remains **RED; not claimed fixed**.

Evidence: `r3/stop_receipt.json` binds eight RD2 checkpoint rows with no structural alias-to-base field and empty `sources`, `source_grafts`, `source_turns`, and `supersedes` on the edge. The historical edge/base payload widths are 49 + 61 = 110 tokens, beyond the C2 arena width 96. These are existing checkpoint observations, not a new fit run. RD2's original report is `/mnt/ForgeRealm/wt/grm-rd1/artifacts/grm_rd2/REPORT.md`; all eight inspected aliases mounted only the edge and returned a refusal.

The existing end-to-end fold contrast in `artifacts/grm_scout_fix5/gpu/summary.json` reports 13/13 accepted folds, coverage 0.8–1.0. In its turn-17 digest, the Jasper base values survive; in turn 26, the Signal-to-Base relations survive, **in a different digest**. At turns 85, 91 and 95, Outpost values and their Handle aliases coexist in accepted digest text. This supports the ability to preserve both relation and value when they are supplied together. It is not a Signal-edge/base merge experiment, a width proof, or a recall gate. The older `artifacts/grm_scout_fix5/summary.json` is a CPU-only report with `gpu: NOT_RUN`; the later `gpu/summary.json` is the evidence cited here.

| Option | Mechanism and touched surfaces | Costs and unresolved constraints |
| --- | --- | --- |
| (a) Two-hop read | Mount the edge; read its base identifier; re-route within the same turn and replace the edge mount with the base mount. Reuse `scripts/grm_e2e_session.py::_probe_ladder_chat` / `_demand_trip` and `core/grm_demand.py::demand_query_text`, with admission and fit in `core/graft_arena.py`. Carry the read alias relation in the same turn's query/prefix so the second read can connect the base value to the original question. | One extra re-prefill plus intermediate identifier decoding, route/page-in and final read. No measured milliseconds or fit guarantee. Each mount must fit separately; live prefix consumes live context. Current C2/r3 uses `max_trips=1`, `demand_ngh=false`; existing machinery needs a separately specified extension, not a switch asserted to already solve this. Missing edges, cycles, ambiguous bases, corrections between reads and termination need explicit semantics and receipts. Stored text can stay unchanged. |
| (b) Fold-merge | The librarian selects the alias edge and current base as a fold job, then FIX-5's source enumeration produces one digest containing both names, relation and value. Touch `core/graft_repository.py::_fold_once` job selection and `core/graft_arena.py::_consolidation_prompts` / `consolidate`, source lineage, retirement and admission indexing. A single digest mount can answer **if** it is complete and fits. | Background/deposit-side consolidation work, source loading, one digest generation/capture and persistence. Existing generation bound `max(120,24*N)` with coverage ≥0.70 remains only a lexical/QC guard; it does not prove relation fidelity. New pairing is required: existing turn-17/26 folds separate the exact Signal evidence. Tokenize the generated digest against 96 seats before claiming single-mount fit; handle split/non-fit honestly. Revision changes must invalidate or supersede stale merged values; include missing-base and alias-cycle cases. No extra per-query re-prefill after a valid merge. |
| (c) Alias-in-base rewrite at deposit | On alias deposit, resolve the current base and amend its stored text to include the alias as an identifier, e.g. a record naming Signal, Base and Jasper together. Touch deposit/command parsing, `core/graft_repository.py::correct_memory`, metadata/index updates, payload capture and WAL/reload. Use a new version superseding the old record, consistent with existing node-level supersession semantics. | Moves lookup and recapture cost to every alias deposit or rename. Stored text changes, so old K/V cannot be retained unchanged. Identifier index, native metadata and durable payload must agree atomically. Text growth and repeated aliases can exceed 96 seats; alias deletion/reassignment and later value correction require propagation. Node-wide retirement can remove unrelated facts in a shared base unless the replacement preserves them. Wider semantic and persistence impact than a fold-job experiment. |

The order's r3 run must measure the residual with FIX-7 absent and all aliases retained. None of the options warrants converting its expected failures into passes. These options are design proposals only; a future order must register success criteria before implementation or gates.

## Prior art

- **Verified local, GRM contributors (2026):** SC1/SCOUT-FIX-1 question-plus-prefix demand re-routing; FIX-5 source-enumerated consolidation and digest lineage; M5/L2 and `correct_memory` explicit supersession, payload recapture and persistence. Taken: existing machinery and its contracts. Proposed here: where David's three alias mechanisms would attach and the costs/residuals to measure. **No prior art known to me for this exact GRM integration.** No new algorithm implemented; there is no implementation code site for the three memo-only proposals.
- **Press et al. (2022), [Measuring and Narrowing the Compositionality Gap in Language Models](https://arxiv.org/abs/2210.03350):** self-ask with search answers intermediate questions. Taken as a conceptual antecedent for (a)'s read-then-follow-up retrieval, not its prompt, scoring or published performance.
- **Sarthi et al. (2024), [RAPTOR](https://arxiv.org/abs/2401.18059):** recursively summarized retrieval representations are an antecedent for (b). Taken: combining source information into retrievable summaries, not RAPTOR's clustering or tree construction. Neither paper validates GRM alias semantics.
- For (c), local `correct_memory` supplies the concrete prior implementation. Database denormalization/materialized-view maintenance is an additional **unverified — lead to check** lead; search terms: `Gupta Mumick 1995 maintenance of materialized views denormalization update propagation`. No novelty claim for moving join work to writes.

Evidence classes throughout: existing end-to-end receipts, checkpoint metadata/source inspection, external literature for antecedents, and explicitly labelled reasoning for the recommendation. No new inference or acceptance result.
